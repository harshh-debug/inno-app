# Innogeeks backend

Express, Prisma, and PostgreSQL foundation for the Innogeeks Phase 1
recruitment platform. Product behavior is defined in `.codex/PRD.md`; the
module-by-module delivery order is in `.codex/IMPLEMENTATION_PLAN.md`.

The implemented Android app integration contract, including request/response
payloads, authentication flow, and error codes, is documented in
[`docs/APP_API_CONTRACT.md`](./docs/APP_API_CONTRACT.md).

## Local setup

1. Review the generated local `.env` and change its development password if desired.
2. Install dependencies with `pnpm install`.
3. Start PostgreSQL with `pnpm db:up`.
4. Apply the development migration with `pnpm prisma migrate dev`.
5. Generate Prisma Client with `pnpm db:generate`.
6. Run the API with `pnpm dev`.
7. In a second terminal, run the email worker with `pnpm worker:email`.

`GET /health` is a liveness check. `GET /ready` verifies PostgreSQL through
Prisma and returns `503` until the database is reachable. PostgreSQL is the only
stateful dependency: the email queue is the `email_jobs` table, so readiness
covers mail delivery too. Product routes will
be added below `/api/v1/public`, `/api/v1/admin`, and `/api/v1/app`.

PostgreSQL is published only on `127.0.0.1:5433` by default, keeping it separate
from the existing local service that uses port `5432`.

Docker Compose also starts Mailpit for local email delivery. It listens for SMTP
on `127.0.0.1:1025` and exposes its local inbox/API on `127.0.0.1:8025`; it
never delivers messages to real recipients.

Authentication requires distinct `JWT_SECRET` and `VERIFICATION_HASH_SECRET`
values of at least 32 characters. To create the initial admin, set
`ADMIN_SEED_EMAIL` and `ADMIN_SEED_PASSWORD` locally, then run `pnpm admin:seed`.

Useful commands:

- `pnpm typecheck`
- `pnpm build`
- `pnpm db:validate`
- `pnpm db:logs`
- `pnpm db:down`

`pnpm db:down` preserves the local PostgreSQL volume.

## Deploying

The app runs on Render and PostgreSQL on Neon; `render.yaml` is a Blueprint for
a single free web service. Postgres is the only stateful dependency, so nothing
else needs provisioning.

Set these in the Render dashboard (they are marked `sync: false`, so the
Blueprint deliberately does not carry them):

- `DATABASE_URL` — the Neon **direct** connection string, i.e. the host *without*
  `-pooler`, keeping `?sslmode=require`. Request traffic would tolerate the
  pooled endpoint now that the purge lock is transaction-scoped, but
  `prisma migrate deploy` needs the direct one and the build runs both.
- `SMTP_HOST`, `SMTP_FROM`, `SMTP_USER`, `SMTP_PASSWORD` — a real provider on
  port 587. Mailpit is local-only and delivers nowhere; the worker's env schema
  rejects `SMTP_USER` without `SMTP_PASSWORD`.

`JWT_SECRET` and `VERIFICATION_HASH_SECRET` are generated by Render, and
`APP_URL` is wired from the service's own external URL so email links cannot
drift from the deployment.

Free-tier behaviour worth knowing, all of it commented in `render.yaml`:

- The email worker runs inside the API process (`WORKER_IN_PROCESS=true`),
  because the free tier has no background worker service. On a paid plan, drop
  that variable and add a `type: worker` service running `pnpm start:worker`.
- Migrations apply at the end of the build rather than in a pre-deploy step, so
  they land while the previous version is still serving. Fine for additive
  migrations; run destructive ones manually first.
- The service sleeps after ~15 minutes of no traffic, so the 6-hourly
  account-deletion purge runs on wake rather than on schedule. Anonymization is
  idempotent and safe to run late, but meeting the 14-day deadline predictably
  needs a cron job or a paid instance.
- `EMAIL_POLL_INTERVAL_MS` is raised to 30s so Neon's compute can autosuspend.
  At the 1s default the database never idles, which would run to roughly 730
  compute-hours a month against a free allowance near 190.
